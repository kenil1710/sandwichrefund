# Feasibility

Step 0, before any contract code: can GenLayer validators read real sandwich attacks from public chain data, and do two independent RPCs agree on every field the rule uses? Every case below was read from **both** Ethereum RPCs (https://rpc.mevblocker.io, https://eth-mainnet.public.blastapi.io) from a Mac and again **inside GenVM** by a throwaway probe contract on Studio Dev (`0x7b5816A505a8d4C1814Fa0e3Fa17406908393509`, deploy tx `0xd59cbdc241449faffcf72e3af3cd3e78b999df6574f7acbee14f1f8b1f056cbc`; not part of this repository). Generated by `tools/feasibility.mjs` and `tools/feasibility_md.mjs` from [feasibility.json](feasibility.json) and [feasibility_genvm.json](feasibility_genvm.json).

## Result

- **65 real Ethereum swaps** in blocks 26230913-26232413 (about five hours of 2026-10-20), every one through one of the 11 covered routers.
- **18 SANDWICHED** (from 9 sandwich bots, 5 by jaredfromsubway.eth), **16 CLEAN**, **31 UNCLEAR** (ambiguous: multi-hop victims, bundles with several victims, partial patterns, unpriced profit tokens).
- Both RPCs returned identical facts for **65/65** cases from the Mac.
- The GenVM probe's facts are **byte-for-byte identical** to the Mac's for **65/65** cases; GenVM consensus (leader + validators, each reading both RPCs) accepted every read.
- Raw `eth_getLogs` filtered by pool + both Swap topics + one block, from inside GenVM on both RPCs: 0xf774c0..9b95 block 26230931: 3 logs, RPCs identical: true; 0xe0554a..939f block 26231053: 4 logs, RPCs identical: true.
- Measured limit: a first GenVM pass read three cases per transaction and 24 of 65 reads came back HTTP 429 from rpc.mevblocker.io (the leader and every validator read at once). Read again one case per transaction, all 65 answered. The contract therefore files exactly one case per transaction; an RPC refusal is UNVERIFIABLE and the case can be filed again.
- The threshold (10 readable real sandwiches) is met. Contract code started after this.

## What is read, per case (one RPC; the contract does it for both)

1. `eth_getTransactionByHash`, `eth_getTransactionReceipt`, `eth_getBlockByNumber("finalized")`, `eth_chainId` (one batch).
2. The receipt's Uniswap V2 / V3 `Swap` logs name the victim's pools. One batch: `eth_getLogs` for those pools, both Swap topics, the victim's block and the next; `token0()`, `token1()`, `factory()` (and `fee()` for V3) of each pool.
3. One batch: the factory's `getPair` / `getPool` for each pool (a look-alike pool fails), and `eth_getTransactionByHash` for every other transaction with a swap on those pools in the block (its sender).
Responses stay small: the logs are filtered by pool, topic and two blocks; at most 4 pools and 40 transactions are read per case.

## Base

A pattern scan of 300 Base blocks found thousands of same-recipient opposite-direction pairs (arbitrage bots trading every block), and one of the two candidate RPCs (base-rpc.publicnode.com) refused receipts of blocks a few minutes old as archive requests. Base was not pursued: the canonical pool and the contracts cover Ethereum only, and the chain table (`CHAINS` in contracts/shared/common.py) holds Ethereum alone.

## How the cases were found

A scan of every Uniswap V2 / V3 Swap log in the range (topic filter, 10 blocks per request) listed same-pool, same-actor, opposite-direction pairs around another swap; each candidate whose transaction went to a covered router was then read and judged exactly as the contract does. The CLEAN cases are router swaps sampled across the range. `data/cases.json` holds the list; the keeper finds the same candidates on its own scan.
